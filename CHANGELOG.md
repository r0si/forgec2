# Changelog

All notable changes to ForgeC2 will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Fixed
- **An allowlist entry typed with capitals never matched.** Both origin gates (`server.allowedOrigin` for the WebSocket upgrade, and `config.AllowedOrigin`) compared the browser's `Origin` host with an **exact, case-sensitive** string, but hostnames are case-insensitive (RFC 4343). An operator who added `MyHost.com` to `server.allowed_origins` — and browsers send the host lowercased — was **still refused**, with nothing explaining why. Both copies now normalise with `ToLower`/`TrimSpace` (a padded hand-edited YAML entry works too), keeping the deny-by-default behaviour: an empty list still admits only `localhost`/`127.0.0.1`/`::1`, a suffix lookalike (`example.com.evil.test`) is still refused, and a malformed `Origin` is refused rather than guessed. `allowedOrigin` **100%**, `config.AllowedOrigin` **0 → 100%**; `internal/server` **65.1% → 65.2%**, `internal/config` **81.7% → 83.2%**.
- **The most common legacy malleable profile could not be imported at all.** `MigrateProfileJSON` decided "this is already v2" from the presence of `server_output` / `client_metadata` / `parameter` — but those keys exist in **both** shapes: a string wire name in v1 (`"server_output":"base64"`) and an array of steps in v2. A v1 profile was therefore classified as v2, the unmarshal failed on the string, and the import aborted with `cannot unmarshal string into ... []malleable.StepV2`. Detection now parses as v2 and, when that fails **and** the document also carries v1-only keys (`beacon_uri`, `user_agent`, `method`, `sleep`, …), falls through to the v1 converter instead of erroring. Both directions are pinned: a v2 profile is never pushed through the legacy converter, a legacy `http_get`/`http_post` profile keeps its URIs, a v1 profile keeps its fields and has its wire-form transforms **parsed**, and a real v2 syntax error still fails loudly. `internal/malleable` **71.7% → 77.7%**.
- **Saving a script executed it — now it only parses.** `LoadScript` validated a script by `RunString`-ing it in the reparse VM, so "save" ran the whole body: a top-level `sendTask(...)` **fired a real task against an agent** just by saving the script, `while(true){}` wedged the save until the parse timeout, and any reference to a per-run binding (`agent_id`, `args`, …) failed with `ReferenceError: … is not defined` because those bindings only exist during a run — so most useful scripts could never be saved. Validation is now `goja.Compile` (parse only): syntax errors are still rejected, nothing executes, and the load path enables the same `console`/`require` surface the runtime installs (a bare VM previously rejected `console.log` at load while accepting it at run time). Covered by a load/unload/execute lifecycle test, the "load does not execute" cases (infinite loop, side-effecting script), `toInt64` coercion of `int`/`int64`/`float64`, runtime errors surfacing as failures, and per-run context bindings. `internal/scripting` **55.2% → 72.4%**.
- **The SSE tool frame could be invalid JSON, dropping a tool result from the transcript.** The `tool` event was assembled with `fmt.Sprintf(`{"id":"%s","name":"%s","result":%s}`, …)`: the tool name was embedded unescaped (a model-supplied name containing a quote breaks the frame) and the result was spliced in raw — but `compactToolResultJSON` deliberately returns **plain text** for a tool whose output is not JSON, so exactly those results produced an unparseable frame. The frame is now marshalled (`buildToolEvent`): a valid-JSON result is carried as an object, anything else as a JSON string, and the name is escaped. Tests cover a JSON result (stays an object), a text result with quotes/newlines/`</script>` (round-trips as a string), a quoted tool name, and an empty result. `buildToolEvent` **83%**.
- **Two bugs came out of covering the AI web-search tool.** (1) Its error paths built the JSON payload with `fmt.Sprintf(`{"error":"…%s"}`, err)`; a message containing a quote — every `Get "https://…"` failure does — produced **invalid JSON** for the tool-result parser. Errors are now marshalled (`aiToolErrorJSON`), and a round-trip test covers quotes, newlines and backslashes. (2) The search allowlist check is now covered in both directions: subdomains pass, lookalikes such as `evilwikipedia.org`, `wikipedia.org.evil.example` and `duckduckgo.com.evil.test` do not.
- **Two backups in the same second overwrote each other.** Found by a flake in the new backup test: `Start` fires an immediate backup while a manual run can arrive in the same second, so both computed the same `forgec2_backup_<timestamp>.fbk` — the second rename overwrote the first on Unix and would fail outright on Windows. Snapshot creation is now serialised (`runMu`, so two concurrent `VACUUM INTO` runs cannot fight over the writer) and the filename gains a `_2`, `_3` suffix when the timestamp is already taken. The lifecycle test now polls for the snapshot instead of assuming which run produced it.
- **A base64-shaped hostname was silently mangled, breaking hostname matching.** `maybeDecodeStoredIdentity` (the restore for implant identity fields stored in base64 wire form) decoded any value that happened to be a valid quartet. `DC01` — one of the most common Windows domain-controller names — decodes to `"\x0c-5"`, which `TrimSpace` reduces to `-5`; the guard accepted it because `-5` contains `-`. The row in the database was correct, but every read showed `-5`: the console displayed a garbage hostname and hostname-based auto-tag rules silently stopped matching that agent. Found while testing the auto-tag sweeper, which read `-5` back from a row that plainly stored `DC01`. The decoder now requires the decoded value to be a **plausible identity** (starts alphanumeric, two or more alphanumerics, only identity characters) and, when the original carries no base64 proof (`+`, `/`, `=`), to contain an address separator (`.`, `:`, `\`); otherwise the stored value is kept verbatim. `WEB1` → `X@u` and `DC01` → `-5` are now both rejected, while real wire form (`MTkyLjE2OC4xLjI0` → `192.168.1.24`, padded values, `CORP\alice`) still decodes. Covered in `internal/db` (the table includes the exact regression) and end to end.
- **Auto-tag matching is covered, and an unknown field no longer matches the fleet.** `autoTagMatch`/`matchOne` were at 73%/33%. A rule naming a field the evaluator does not know compared `""` against the value — so a typo (`hostnmae`) made `equals:""` true and tagged **every agent**. Unknown fields now fail closed. The tests cover every operator (contains/equals/not_equals/starts_with/regex), case-insensitivity, the public_ip alias, `+`-AND-ing of multiple conditions, fail-closed shapes (empty, malformed, unknown operator, invalid regex) and an end-to-end sweep that tags only matching agents, is idempotent on a second run, and does nothing while the rule is disabled. `autoTagMatch` and `matchOne` **100%**; `internal/server` **64.4% → 64.5%**, CI total **51.2%**.
- **The emergency panel no longer fabricates zeros.** `handleEmergencyStatus` logged a failed count and fell through for both figures, so a database error produced `online_agents: 0, pending_kills: 0` — on the one screen an operator reads while deciding whether the fleet is really down. Both counts now answer **500** instead. The test pins what the numbers mean: `online_agents` counts everything that is not `offline` (so `stale` still counts, because a quiet beacon is not a dead one), and `pending_kills` counts only `kill` tasks in `pending`/`running` — completed kills and unrelated task types are excluded.
- **Two more "log and report success" paths are fixed.** `handlePluginDelete` dereferenced `s.pluginManager` with no nil check whenever the plugin had a name — the same panic the toggle had, on the delete path; it now guards the manager and still removes the row. `handleAutoTagApply` answered **200** with `{"applied":0,"partial":true,"error":"batch insert failed"}` when the whole batch failed; nothing reads `partial`, so the failure surfaced as success. It now answers **500**. The plugin-delete guard is covered by a test (delete works and no panic without a manager); the autotag failure branch cannot be exercised without forcing a batch-insert failure, which is recorded rather than claimed.
- **The plugin toggle could panic on a nil manager and could report a state the runtime never adopted.** `handlePluginToggle` called `s.pluginManager.SetEnabled` whenever the plugin row had a name, with no nil check — a server built without a plugin manager (tests, or any build with plugins disabled) would panic on the dereference. It now guards the manager, and when the manager **rejects** the change it reverts the row and answers **409** instead of returning the row's optimistic value: the console would otherwise show a plugin as enabled while the runtime kept it disabled until the next restart. The test pins the nil-manager path (toggle persists, no panic), the no-body flip, and that an unknown plugin is a 404 rather than a silent success. `handlePluginToggle` **59%** (the manager-rejection branch needs a real manager, which is why it stays uncovered).
- **The listener detail page no longer shows a reassuring zero when the count fails.** `handleListenerDetail` logged a failed `COUNT(active agents)` and then **fell through**, responding `ActiveAgents: 0`; the detail page renders that number prominently, so a transient database error read as "this listener has no live beacons". It now answers 500 like the neighbouring agent query does, and the page shows its error state instead of a fabricated figure. The new test also pins what the number means: only agents seen within `ListenerActiveThreshold` count, and an agent from another tenant never appears in `Agents` at all. `handleListenerDetail` **70% → 78%**.
- **The "stale" agent band was 180 nanoseconds wide, so stale agents were reported as offline.** `staleThreshold()` computed `time.Duration(d) * StaleThresholdMultiplier` where `d` is a threshold in **seconds**: the result was a nanosecond value, so the band `(offline, stale]` collapsed and any agent older than the offline threshold landed in **offline**. The agents page, the dashboard counts and the REST v1 list all bucket through this helper, so a fleet that had been quiet for two minutes showed as offline rather than stale. The multiplication now includes `* time.Second`; a regression test asserts the stale threshold is `multiplier * offline` **and** strictly wider than the offline threshold, and the filter test pins an agent seen two minutes ago to the stale bucket. `implantListQuery` **63% → 95%**, `staleThreshold` **100%**.
- **The agent signaling socket is covered, and its error-frame cap was dead code.** `handleRDWebRTCAgent` was at 0%. The tests now pin the token guards (missing session/token → 400, unknown token → 401, a valid token presented for a different agent id → 401 with no agent attached), the loop (the operator is told `agent_ready`; `answer`, `ice` and `state` frames reach the operator; an empty answer is dropped; `stop` ends the session) and the single-use token (a second dial with the same token is refused as 401 — the handler's 409 "already has an agent" branch is therefore unreachable, which is recorded rather than silently deleted). Writing the test exposed a real defect: the `error` frame truncated `msg.Reason` to 512 bytes and then forwarded the **original** bytes, so an agent could relay an error reason as large as the whole read limit; the truncated frame is now re-marshalled and sent. `handleRDWebRTCAgent` **0 → 79%**; `internal/server` **62.3% → 62.5%**.
- **Remote-desktop signaling was dead whenever the browser connected before the agent.** `webrtcSession.attachOperator` returned *agent readiness*, but `handleRDWebRTCSignal` used the value as *attach success* and closed the socket on a false return. The operator dials as soon as it has the session while the agent attaches after a round trip — the common order — so the signaling socket was killed immediately, no frame ever reached the browser, and remote desktop could not work. It now reports attach success and readiness is queried with `agentAttached()` (the operator is told `waiting` until the agent arrives). Found while trying to test the handler: the test saw an empty socket on every dial. A regression test drives the loop — `waiting` on connect, `pong` for ping, an error frame for an unknown type, an offer buffered while the agent is absent, an empty offer rejected. `handleRDWebRTCSignal` **22% → 59%**.

- **The settings save handlers raced the beacon hot path on the live config.** `handleSaveAgentConfig`, `handleSaveServerConfig`, `handleSaveMalleableProfile` and `handleRegenerateJWT` mutated `s.cfg` (scalars, strings and the Malleable header maps) with no lock, while the config reloader swapped the same struct under `s.configMu` and ~40 read sites — the per-beacon malleable wrapper, the auth session path, the metrics collector, the settings page itself — read it under `RLock`. A save landing next to a beacon was a data race on live config state, and the settings page handed the Malleable header maps to the template **by reference**, so a concurrent save replaced a map the render was still walking. The save handlers now hold `s.configMu` across mutate → validate → save (one atomic window; the file watcher's reload takes the same lock and can no longer observe a half-applied edit), the settings page and the `/api/settings` JSON endpoint read a single locked snapshot, and the composed threshold getters (`offlineThreshold`/`staleThreshold`/`offlineThresholdFor`, the retention getters) take the lock exactly once through an unlocked core — nested `RLock` calls would have deadlocked the moment a writer queued between them. `go test -race ./internal/server/...` is green; `settings_config_race_test.go` pins the save-vs-beacon-reader and save-vs-settings-page overlaps.
- **The DNS C2 surface had the same race class.** The `s.dnsListener` pointer was read by the status poll, swapped by start/stop and closed by shutdown with no lock at all, and `handleDNSStart` mutated the DNS config fields under `cfg.Lock()` — a *different* mutex than the `configMu` every other config reader holds, so the two never excluded each other; a console polling `/api/dns/status` raced any start/stop on both the pointer and the config. The pointer now moves under a dedicated `dnsListenerMu` (held across check → bind → publish, which also closes a start/start TOCTOU that could leak a bound socket), the DNS config fields move under `configMu` like every other field, and the extra-listener and generate paths read them under `RLock`. `dns_handler_race_test.go` pins both overlaps.
- **The remaining readers of settings-writable config completed the discipline.** The SPA middleware's `malleableEnabled()`, the `logging.level` reload hook, the TCP accept loop's error log, the shell / agent-config / generate page renders, the audit page's auth flag, the password-complexity policy and the "Download Config" redaction list all read fields the settings saves (or a hot `CopyFrom`) mutate, without the lock — including the crown-jewel secret snapshot, where a torn read could have left a real secret unredacted in the download. Every one now reads under `configMu.RLock` (the TCP listener captures its bound address once, since the socket keeps it for life regardless of later edits). `go test -race ./internal/server/...` green.
- **The Rules-of-Engagement gate and auto-recon read a hot-reloadable config.** `Roe.Enabled`, `DenyCIDRs`/`AllowCIDRs`/`DenyDomains`/`AllowDomains` and `Server.AutoRecon` are swapped under `configMu` by the reload watcher's `CopyFrom`, but `checkRoE` / `checkRoELoaded` (every task-creation path) and `queueAutoRecon` (on every new beacon) read them without a lock — a torn read of a slice header could evaluate a target against a half-old/half-new allow list. The gate now snapshots the whole section under one read lock, and auto-recon reads the allowed types under the same lock, so an in-flight reload is atomic to each task decision.
- **A per-run config copy carrying a live secret could have been committed.** `.gitignore` excluded only `config.yaml`, so `config.audit.yaml` (a copy with a plaintext `jwt_secret`) sat untracked-but-addable at the repo root — one `git add -A` would have committed it. `config.*.yaml` is now ignored, with the shipped `config.example.yaml` kept as the exception.
- **The last unlocked config readers, and a gate so the class cannot come back.** Beyond the settings/DNS/RoE surfaces, 83 functions still read `s.cfg` — which the reload watcher rewrites in place under `configMu` — without ever taking the lock: the shared data-dir helpers on every screenshot/upload/payload path, the seven `sync*` reload hooks, the operator-plane and metrics middlewares (both run per request), the screenshot/backup/cert/stager/phishing/redirector/update-check handlers, and the metric-alert evaluator. All 83 now either take a read-lock snapshot (`rawDataDir()`/`implantDataDir()`/`backupDir()`/`backupKeyHex()`/`phishingBaseURL()`/`lportFwdAllowed()`/… for the shared helpers; inline snapshots for the handlers) or carry an explicit `// config-lock:` marker naming why they cannot race (boot-only, constructor, or a caller that holds the write lock). `TestConfigReadsAreLocked` walks the package sources and fails on any function that reads `s.cfg` without the lock or a marker, so the next unlocked read breaks CI instead of shipping.

### API

- **Success responses now have one shape: `{"success": true, "data": ...}`.** `respond()` wraps the payload exactly once and `respondSuccess()` is gone, so a handler can no longer emit a bare payload while another emits the envelope. The 87 sites that hand-built `respond(c, gin.H{"success": ...})` are migrated (the two whose payload was a nested `data` map now pass the inner map), including the multi-line ones. `respondError` already produced `{"success": false, "error": ...}`, so the contract is now symmetric.
- **Two real UI bugs fell out of the migration.** `/stager/tokens` and `/redirectors` returned their list under `data`, but the pages read `res.success ? res.data : []` / `data.redirectors` *after* `api.ts` had already unwrapped the envelope — so the stager token list and the redirector list were **always empty**. The stager page now reads the array directly and `/redirectors` returns `{redirectors, total}` (the key the page actually reads); the Go test that pinned the old `data` key was updated with it.
- **The OpenAPI spec now documents the envelope it actually sends.** 108 JSON 200 schemas still described the bare payload, `SuccessResponse` was the stale `{success, message}` and the spec's own `version` said 2.6.2. Every JSON 200 schema is now `allOf: [SuccessResponse, {data: <payload>}]`, `SuccessResponse` carries `data`, the spec version matches `VERSION`, and `scripts/apply-openapi-envelope.mjs` (with `--check`) runs as `check:openapi-envelope` inside `npm run check` — so a new handler or a re-added bare schema fails the gate instead of drifting silently. `check:openapi-types` only compared the spec to the generated types, which is why this went unnoticed.
- `TestSuccessEnvelope` is the ratchet for the remaining half: it rejects any hand-built envelope outright and pins the per-file count of raw `c.JSON(http.StatusOK, ...)` sites in `internal/server/envelope_baseline.txt`, failing when a file grows (new debt) or shrinks (stale baseline). **The migration is now complete**: 336 sites at the start, and the baseline holds only five documented exceptions — `respond()` itself, the four REST v1 list endpoints whose `{success, data, total}` shape is published in `api/openapi.yaml`, the external-C2 protocol reply struct, the page-document renderer, and `/health` (container and deploy probes read `status`/`version`/`uptime` at the top level). Each carries its reason in the baseline file.
- **Batch 1 of the migration: settings, monitor, task acks.** `handlers_settings.go` (9 sites) now returns `{message}` / `{}` payloads, `handlers_monitor.go` (17) is fully converted, and the shared task-ack emitters (`task_dispatch.go`'s `{task_id}` and `handlers_files.go`'s `ls`/`push` acknowledgements) moved to `respond`, so every file operation now yields one shape. The REST v1 *list* endpoints in `api.go` deliberately stay on the documented `{success, data, total}` body (recorded in `api/openapi.yaml`); their single-object siblings were byte-identical and moved to `respond`.
- **Two more latent UI bugs, same family.** `/api/automation/rules` returned its list under `data` while the page reads `rules ?? data` off the *unwrapped* payload, and `/api/webhooks` did the same — so the automation rules and webhooks lists rendered empty. Both now return the keyed payload the page reads (`{rules, total, page, page_size}` / `{webhooks}`).
- **Batch 2–4: dashboard, users, listeners.** `handlers_dashboard.go` (8 plain payloads, byte-identical through `respond`), `handlers_users.go` (7 message acks), `handlers_listeners.go` (6: the list now returns `{listeners, total, page, page_size}`, detail keeps `{listener, agents, total, active}`, enable/disable return `{message}`) and `handlers_automation.go` (5 remaining) are at zero raw 200s. Baseline: **336 → 201**.
- **A fifth empty-list bug and a test-isolation fix, both found while converting.** The users page read `d.success`/`d.data` off the already-unwrapped `/api/roles` response, so the custom-role list in the user dialog was always empty; it now reads the array directly. `TestHandleDashboardCredentialTypes` only passed when another test in the package had already initialized loot encryption and left implant rows behind — it now initializes both itself and passes standalone.

### Fixed

- **BOF uploads were rejected outright.** `handleBOFUpload` called `validateUploadExtension(file.Filename, ".o,.obo")`, but the first argument is the allowlist *key*, not the filename: the lookup fell through to the generic text allowlist, which never matches `.o`, so every upload answered 400 "file extension not allowed". It now passes `("bof", file.Filename)`, using the `bof` allowlist that already existed. Regression tests cover a COFF object succeeding plus a PE-as-BOF and an `.exe` being rejected by the magic/extension gates.
- **Four handlers read a context key that is never set.** They asked for `c.GetString("username")` while the auth middleware only sets `"user"`, so the value was always empty: `db.BOFFile.CreatedBy` (upload and repo import), `db.Script.CreatedBy`, and the `scripting.Caller.Username` handed to the script engine. All four now read `"user"`.

### Security
- **The webhook validator accepted hosts it could not resolve, and missed multicast/CGNAT.** `validateWebhookURL` carried its own copy of the address policy: it ignored a DNS resolution **failure** (`if err == nil`), so a hostname that did not resolve at save time was accepted and then dialled once it did — the classic DNS-rebinding shape — and it did not reject multicast or CGNAT targets. The policy now lives in one shared `nonPublicHostError` helper (netip + unmap + loopback/unspecified/private/link-local/multicast + `0.0.0.0/8` + CGNAT), with resolution failure treated as an error. Delivery re-validates the URL at fire time as well, so a target that later resolves to a private address is still refused. Tests pin both directions, including `172.15`/`172.32` and `100.63`/`100.128` just outside their ranges, and the existing webhook tests moved from `example.test` to a public literal so they no longer depend on DNS. `validateWebhookURL` **74% → 87%**.
- **The outbound-fetch guard could be walked past `0.0.0.0` and IPv4-mapped forms.** `isPrivateIP` — the check standing between a plugin's `http.request` and the server's own loopback services — matched **string prefixes** (`10.`, `192.168.`, `127.`, …). It returned false for `0.0.0.0`, which connects to the local host on Linux, for `::ffff:127.0.0.1`, for bracketed literals like `[::1]`, and for the `::` unspecified address. It now parses with `netip`, unmaps IPv4-mapped addresses and asks `IsLoopback`/`IsUnspecified`/`IsPrivate`/`IsLinkLocal*`/`IsMulticast`, adding CGNAT (`100.64.0.0/10`) which the standard predicates do not cover. The table pins both sides, including `172.15`/`172.32` and `100.63`/`100.128` just outside their ranges, and the bridge test proves private targets (`0.0.0.0`, `[::1]`, the metadata address, RFC1918) are refused before any request is made. `isPrivateIP` **81% → 100%**, `HTTPRequest` **75%**.
- **`LogConfigChange` wrote secret values into the audit log.** The details string paired the values with the keys `old`/`new`, and `sanitizeDetails` only redacts by the key it sees — so a change to a sensitive field (for example `jwt_secret`) recorded **both the old and the new secret** in a long-lived, admin-readable, chain-hashed table. The helper has no callers today, which makes this latent rather than exploitable, but it is exported and any future settings handler would have inherited the leak. Sensitive field names (`secret`, `password`, `key`, `token`, `credential`, `cookie`, `session`, matched case-insensitively and deliberately broadly) now record `values redacted (sensitive field)` while still naming the field that changed; a non-sensitive field keeps `old=… new=…` so tuning changes stay useful. The three operator-audit helpers are covered (**100%** each) including the nil-context `system` attribution and that every row carries its chain hash.
- **The unauthenticated payload download is pinned against traversal.** `handleServePayload` (the `/payloads/:id/:filename` route, which needs no login so a stager can be fetched) was at 0% and builds its path from two URL segments. The test drives five traversal shapes — `id=".."`, `../../../config.yaml`, Windows separators, `....//`, a dot-rooted path — against a decoy `config.yaml` planted above the payloads root, and asserts only the refusal bodies come back (`forbidden`, `Invalid path`, `not found`); no bypass was found, the containment check holds. The missing-payload branch now answers `not found` with a body instead of a bare `c.Status(404)`, which keeps the status observable on a recorder and gives clients something to log. `handleServePayload` **0 → 100%**.
- **The integrations view of the webhook table was not tenant-scoped, and its rows never fired.** Two handlers manage the same `WebhookConfig` table: the automation one was scoped correctly, the `/api/integrations` one was not. A probe showed an integration created by a tenant-1 operator was stored with `tenant_id = 0`, and because webhook delivery matches `tenant_id = event.TenantID`, that integration **silently never fired** for any tenant-scoped event. The same handlers listed every tenant's webhooks and let `findOrFail`/an unscoped delete act on another tenant's row — a tenant-1 admin could retarget or delete a tenant-2 webhook, redirecting that tenant's event payloads (hostnames, findings). Creation now stamps the caller's tenant, the list goes through `tenantScope`, update/toggle use `findTenantOrFail`, and delete is tenant-scoped with a 404 when nothing matched. The new test proves stamping, list isolation, and that a foreign row cannot be toggled, updated or deleted.
- **The generated payload URL trusted the Host header, and the Host ends up inside the generated commands.** `handleGenerateOneLiner` built the download URL as `scheme://<request Host>/payloads/...` and interpolated it, unescaped, into every one-liner it returns (PowerShell single-quoted strings, `certutil`, `curl`). A spoofed Host therefore either pointed the operator's download at another server or broke out of the quoting entirely — e.g. `evil.example'; Start-Process calc; '`. A new `sanitizeRequestHost` accepts only hostname[:port] and bracketed IPv6 and rejects quotes, spaces, `;`, `$`, backticks and out-of-range ports; the handler answers 400 for an invalid Host, and the WebRTC TURN URL builder uses the same validator instead of trusting `c.Request.Host` verbatim. Covered by a 21-case accept/reject matrix plus a handler test that posts an injected Host and asserts nothing reaches the response.
### Security

- **User management was not tenant-scoped, and two paths were exploitable.** A probe showed a tenant-1 admin's `/users` page payload contained tenant-2 accounts, `handleAddUser` created rows with `tenant_id = 0` (the legacy unscoped bucket every tenant can see), and `handleSetUserPassword` updated `password_hash` **by id with no scope** — so a tenant-1 admin could reset a tenant-2 user's password and sign in as them. The page now lists through `tenantScope`, creation stamps the caller's tenant, and every user lookup uses `findTenantOrFail` (a foreign id answers 404). A same-tenant reset still works and revokes the target's sessions.
- **The tenant lookup in `handleAddUser` deadlocked its own transaction.** The first version resolved the tenant inside `s.db.Transaction`: the nested query waits for a connection the transaction already holds (a single-connection SQLite pool), and the test hung for three minutes instead of failing. The tenant is resolved before the transaction opens.

- **Six 5xx responses echoed raw internal errors, and a gate now prevents it.** The generation handlers answered 500 with `err.Error()` for v3 registration-secret and implant-config failures, and the reverse-port-forward bind error included the raw socket message — all of which can name key material, absolute paths or local addresses. They now log the real error and answer with `sanitizeError`. `scripts/check-error-sanitization.mjs` (`check:error-sanitization` in `npm run check`) walks every `respondError(..., StatusInternalServerError, …)` call and fails when the message is a raw error rather than a literal or a sanitizer; verified in both directions with a probe file. It scanned 1,277 5xx call sites clean after the change.
- **`POST /api/update-check/refresh` was open to every authenticated role.** It forces an outbound GitHub API call and rewrites the update state, but was registered on the root auth group with no permission middleware, so a viewer could trigger unlimited egress; it now requires `settings.write` (the status endpoints stay readable). A router audit cross-checked all 374 mutating routes against their group middleware: the only remaining ungated ones are the two login endpoints and the self-service session extend/logout, which are intentional. A source-contract test keeps the permission middleware (and the admin requirement on hot-update) from being dropped in a refactor.

## [2.7.1] - 2026-10-23

### Upgrade note

- **2.7.0 cannot update itself.** Its update checker asked `forgec2/forgec2` for
  releases and read the 404 as "up to date", and even a release it did see could
  not be installed or restarted (wrong asset, lost `-config`, no rollback). Update
  a 2.7.0 installation by hand once: download the 2.7.1 binary for your platform
  (or the one-click archive), stop the server, replace `forgec2-server[.exe]`,
  start it again. From 2.7.1 on, the console's **update now** works, and every
  later release can be installed from the browser.
- The hot update needs the release to carry `forgec2-server-<os>-<arch>[.exe]`
  plus its `.sha256`; the release workflow builds exactly those names, and a
  release without a binary for the running platform is refused instead of
  guessed at.

### Fixed

- **The hot update could never succeed.** The release asset was chosen by a hard-coded `".exe"` suffix plus a loose name match (`windows` / `amd64` / `x64`), so a Linux or macOS host found no binary at all and an arm64 host could be handed the amd64 one. The checksum was taken from whichever `*.sha256` happened to be listed first — in a multi-platform release that is another platform's checksum, so the verification ended in `checksum file has no entry for …`. The selector now derives the exact asset name from the running platform (`forgec2-server-<os>-<arch>[.exe]`, with the usual architecture spellings) and derives the checksum from the selected binary; a release that carries no binary for this platform, or more than one, is refused instead of guessed. The release repository is stamped into the binary (`internal/buildinfo.Repo`, injected by the release workflow), so a fork checks its own releases.
- **The hot update never restarted the server.** The update worker was registered in the server's own waitgroup and then waited for that waitgroup, so it blocked forever, and only the context was cancelled — the HTTP server was never shut down. The console sat on "restarting" while the old build kept serving, and the restart script then copied over a running binary (Windows: the copy failed and the freshly downloaded binary was deleted). The process now shuts down properly and hands the swap over to a generated restarter.
- **The restart dropped the command line.** The new server was started without any arguments, so `-config` (and `-log-format` / `-log-file`) were lost and a server started with a custom configuration path came back on the default one. The restarter now starts the new build with the original arguments and working directory.
- **A broken release left the service down.** The old binary was overwritten in place with no backup, no health check and no rollback. The previous binary is now kept, the new build has to report a healthy boot (its listener is bound) within 60 seconds, and otherwise the backup — together with the SQLite snapshot taken before the swap — is restored and the old build is started again. The outcome (`success` / `failed` / `rolled_back` / `interrupted`) is audited and readable at `GET /api/update-progress`.
- **The update checker pointed at a repository that does not exist** (`forgec2/forgec2`), and a 404 from the releases endpoint was read as "no new release" — so the console always claimed to be up to date and no update was ever offered. A missing repository is now reported as an error, and `is_latest` is only true after a check that actually succeeded (`check_ok` / `check_state` were added to the payload).
- A second hot-update request while one is running is refused with `409` instead of starting a second download and a second restarter against the same binary; a cross-process lock in `.update/lock` protects an installation that is shared by two instances.
- The restart script no longer stays behind in the installation directory: the restarter lives in `<install dir>/.update/`, is written with restrictive permissions and deletes itself, and the staged download is removed on every failure path.
- Release notes can no longer be cut off by GitHub's 125,000-character body limit: the 2.7.0 changelog section alone is ~125k, so the published page ended mid-sentence. The generator keeps whole lines under a 60k budget and closes with a link to `CHANGELOG.md`, while the one-click instructions, the archive list and the raw binary list stay at the top, above the truncation point.
- The CycloneDX SBOM is really attached now: `forgec2-server-linux-amd64.sbom.json` was generated after `upload-artifact`, so it never reached the release although the notes announced it. The step runs before the upload (the artifact glob carries it), the one-click assembler filters `.sbom.json` out of its `forgec2-server-<os>-<arch>*` match, which could otherwise have packed the SBOM as the server binary, and the command passes `-json`: `cyclonedx-gomod` writes XML by default, so the asset named `.sbom.json` held an XML document; the tag is then stamped into `metadata.component.version`, which the tool leaves empty for a main module.
- The release notes' signature hint showed the signing command (`go run ./cmd/sign-release <file.sha256>`), which needs the private seed and fails for an operator; it now shows `go run ./cmd/sign-release -verify -key <pubkey> <file.sha256>` and points at the published key in `docs/DEPLOY.md`.
- `docs/CAPABILITY_MATRIX.md` follows `VERSION` again: the 2.7.0 bump left its stamp at v2.6.2, which failed the CI docs-freshness gate.

### Changed

- The update banner and the update dialog only offer the installation to an administrator (the endpoint is admin-only, so every other operator used to get a 403), and the dialog now waits for the server to come back after the restart and reloads the console instead of hanging on "restarting". The background check runs with a jitter so a fleet of servers does not poll `api.github.com` in lockstep.

### Security

- **Six 5xx responses echoed raw internal errors, and a gate now prevents it.** The generation handlers answered 500 with `err.Error()` for v3 registration-secret and implant-config failures, and the reverse-port-forward bind error included the raw socket message — all of which can name key material, absolute paths or local addresses. They now log the real error and answer with `sanitizeError`. `scripts/check-error-sanitization.mjs` (`check:error-sanitization` in `npm run check`) walks every `respondError(..., StatusInternalServerError, …)` call and fails when the message is a raw error rather than a literal or a sanitizer; verified in both directions with a probe file. It scanned 1,277 5xx call sites clean after the change.

- Unbound v3 registration secrets now expire at authentication instead of only at the hourly sweep: `server.reg_secret_orphan_ttl_hours` (default 168h = 7 days, hot-reloadable) bounds an unbound build secret, and the auth path refuses one past that age even when the tick has not fired yet, so a leaked build secret cannot enroll an agent long after its build. The sweep also runs once at startup rather than only after the first hour. Secrets already bound to a deployed agent never expire — they are that agent's long-term credential, and deleting one would permanently lock the beacon out
- Hot update refuses to install a release it cannot prove is newer: version comparison now fails closed when either version is not a plain numeric release stamp (a `dev`/nightly build, a build whose version was never injected, or a tag with a prerelease suffix), instead of treating the unreadable side as "older" and accepting an arbitrary published release
- Agent no longer downgrades to cleartext when every configured C2 URL is encrypted: the WSS→HTTP fallback, the DNS→HTTP fallback and transport failover/rotation refuse `http`/`ws`/`h2c`/`tcp`/`udp`/`dns` for such an implant (configure at least one cleartext URL to keep lab failover)
- HTTP(S)/mTLS beacon clients refuse a redirect from an encrypted origin to `http://`; cleartext lab origins keep normal redirect behaviour
- Agent certificate pinning now actually authenticates self-signed teamserver certificates: the pin replaces chain validation (plus a hostname check when a server name is known) instead of failing before the pin is consulted
- Agent DNS answers are validated before use: response bit, rcode, transaction ID, question name and question type must match the outstanding query
- Agent beacon responses are size-capped (16 MiB) so a hostile endpoint cannot make the implant buffer unbounded data
- Operator-plane guard now covers the authenticated `/api/v1` REST surface (only `/api/v1/health` is exempt for probes); `operator_allowed_cidrs` and operator mTLS can no longer be bypassed via API-key/session automation routes
- Audit logs are tenant-scoped: `AuditLog.TenantID` is stamped on write, and both audit read surfaces (operator page + `/api/v1/audit`) plus retention purge return the caller's own tenant plus legacy `tenant_id = 0` rows; the tamper-evident hash chain input is unchanged so historical `EntryHash` values stay verifiable
- gRPC mTLS is fail-closed: a missing/unreadable/unparseable `client_ca_file` with `require_client_cert` refuses to start the listener instead of silently serving without client authentication
- Per-listener TLS fails closed instead of degrading: `require_client_cert` without a client CA (per listener or server-wide), an unreadable or certificate-less `client_ca_file`, a `min_tls_version` other than 1.2/1.3, or TLS knobs on a non-TLS scheme are refused with `400` at the API boundary and refuse the listener start, so a row can never describe a listener that would come up without the check the operator asked for; an extra HTTPS listener whose TLS configuration cannot be honoured is no longer handed to the accept loop at all (the failure used to be logged asynchronously after the listener row was already recorded as running)
- Beacon resync no longer answers unauthenticated frames while the server still holds that agent's session (UUID-existence oracle / response amplifier); AEAD-verified replays and genuinely lost sessions still receive the resync + rekey
- Plugin execution is fail-closed: a process guard that cannot be attached now kills the plugin and refuses the run, `Cmd.WaitDelay` bounds `Wait` when a grandchild holds the output pipes, the guard is released as soon as the context fires, and manifest timeouts are clamped to a 300s server ceiling
- Goja scripts can no longer `require()` host modules (deny-all source loader; `console` still available), script source is capped at 1 MiB, and top-level/event execution is time-bounded (10s parse / 30s callback)
- GitHub Actions are pinned to immutable commit SHAs and every Dockerfile/compose base image to a multi-arch digest (the human version stays in a comment and Dependabot still raises update PRs), removing the mutable-tag supply-chain gap
- Live screen frames no longer reach read-only roles through the notification socket: the dashboard `/ws` screenshot fan-out is filtered by the same gate as the screenshot HTTP APIs (operator identity plus `agents.write`, custom roles resolved through the role table, unknown users fail closed). Previously the tenant check passed a user whose role could never fetch a frame over HTTP, so a read-only account in the same tenant could watch a desktop by holding a socket
- Remote-desktop input is validated and rate-limited at the API boundary instead of being handed to the agent unread: types are whitelisted to `move`/`click`/`key`, coordinates are bounded to ±32767, key names to 1–32 characters, and accepted events are capped at 40 per second per (operator, agent) with an explicit `429`. Every accepted event writes a task row plus an audit row, so an unbounded client was a write-amplification primitive, not just an input flood. The legacy `/ws/remote-desktop` relay applies the same normalization plus a per-connection budget, and the screen-stream `width` parameter is validated (16–16384) and canonicalized before it is spliced into the agent's CSV stream command — an arbitrary string there was parameter injection into the agent-side parser; an unknown `mime` is a `400` instead of being silently ignored, and `mime` without `width` is refused because the agent parses that command positionally
- The legacy `/ws/remote-desktop` upgrade is hardened end to end: the browser origin is checked against the configured allowlist (browsers attach session cookies to cross-site upgrades), the operator key comes from the authenticated session instead of a spoofable query parameter, per-agent (8) and global (64) connection caps are enforced before the upgrade so refusals are real HTTP statuses, a second stream from the same operator replaces and closes the stale socket, and open/close are written to the audit trail. `/rd/:id/screenshot` also records an audit row now
- Agent-scoped pages are tenant-scoped: the screen-monitor page and the token-management page looked up the agent without a tenant filter, so an operator in one tenant could render another tenant's agent page/JSON (identity fields, token entries) by id; both directions now use the scoped lookup and redirect instead of leaking
- mTLS client material is validated before a build starts: a certificate without its key (or vice versa), a pair that does not parse as `tls.X509KeyPair`, a CA bundle containing no PEM certificates, or any single entry over 64 KiB is refused with `400` at the API boundary instead of being embedded into a binary that could never complete the handshake
- The token stager's client private key cannot be read off the build process: the mTLS material is compiled from a generated source file instead of `-X` ldflags (a PEM block also cannot survive `-X`, whose value cannot carry newlines), matching the config-blob rule the agent build already follows; a stager whose material does not parse exits before the fetch instead of silently downgrading to an unauthenticated one
